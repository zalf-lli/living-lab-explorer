# Phase 3.1: Data Source Research & User Validation - Context

**Gathered:** 2026-06-01
**Status:** Ready for planning

<domain>
## Phase Boundary

Deliver a curated, end-user-validated shortlist of candidate geodata and statistical sources. Three artifacts:

1. A defined **inventory / summary format** (the review catalogue).
2. **AI-assisted source summaries** with traceable evidence, separating verified source facts from AI interpretation.
3. Approved sources converted into **integration-ready GSD backlog items**.

This phase produces a decision-backed shortlist that de-risks later integration. It does **NOT** ingest or integrate any data source — every actual pipeline integration is future, separate work.

</domain>

<decisions>
## Implementation Decisions

### Inventory & review catalogue format
- **D-01:** The review artifact is a **spreadsheet catalogue**, extending the existing `data/variables_catalogue.xlsx` pattern (one row per reviewable item, decision + priority columns). Easy to circulate to ZALF colleagues / LL stakeholders.
- **D-02:** A committed **CSV (and/or markdown) mirror** of the catalogue lives in the repo so the inventory is git-diffable and traceable (mirrors the existing `data/destatis_variables_catalogue.csv` precedent). The `.xlsx` is the working/review copy; the committed text mirror is the canonical versioned record.
- **D-03:** The catalogue separates **verified source facts** from **AI interpretation** in distinct columns:
  - *Source-stated / verified columns* — spatial & temporal coverage, access method, licensing/reuse constraints, update cadence — each backed by a citation URL the AI actually fetched.
  - *AI-assessment columns* — integration complexity estimate, LL relevance, caveats — explicitly advisory.
  - Reviewers trust the fact columns; the assessment columns are advisory only. (Satisfies the cross-cutting evidence-chain constraint.)

### Review granularity
- **D-04:** Inclusion decisions are made at **variable / layer level for every source** — each source is drilled down to its individual datasets / layers / GENESIS variables, not just summarized at portal level. This matches what `variables_catalogue.xlsx` already does for DESTATIS GENESIS variables.
- **D-05:** For large catalogue-style portals (INSPIRE Geoportal, DWD CDC, Protected Areas hub), enumeration is **bounded to LL-relevant + agricultural-landscape layers only**. Note the portal's overall breadth in the summary, but do not enumerate the entire catalogue. (Reconciles D-04 with portals that hold hundreds/thousands of layers.)

### Per-item decision fields
- **D-06:** Each catalogue row records: **decision (include / defer / reject) + priority (High / Med / Low) + short rationale**. No per-LL relevance tagging on the decision itself (LL relevance is captured in the AI-assessment column per D-03).

### Research scope & discovery
- **D-07:** The candidate source list is **locked to the user-provided table (see `<specifics>`) plus the entries in `docs/data-sources.md`**. These are the mandatory inputs.
- **D-08:** Discovery beyond the list is **targeted, not broad**: actively hunt for IACS / InVeKoS equivalents for the Living Lab states (especially **Hesse** and **Brandenburg**) and close analogs of the listed themes (climate, protected areas, agricultural statistics, land-use time series). Do not run a broad agri-environmental sweep.
- **D-09:** Sources already in the pipeline — **DESTATIS GENESIS, DLR croptypes, BÜK250 soil** — appear in the catalogue flagged as **"already integrated / in-progress"** rows, so reviewers see the complete data picture and don't re-propose them.

### Integration-ready output
- **D-10:** Approved (included) sources are captured as **GSD backlog items (999.x)** via `/gsd:add-backlog` — a prioritized parking lot promotable into roadmap phases later. Keeps the roadmap clean until each integration is committed.
- **D-11:** Each backlog item carries an **integration sketch**: access method, data format, pipeline path (raster / vector / tabular), rough complexity estimate, and which of the 5 LLs it serves. Enough detail for a future planner to scope the integration phase without re-researching.

### Claude's Discretion
- Exact column set, ordering, and sheet/tab structure of the catalogue (within the D-01/D-03 constraints).
- How the AI research is conducted per source (web fetch, WFS/WCS `GetCapabilities` probing, STAC queries) so long as every verified fact carries a citation and the source-fact / AI-assessment separation (D-03) holds.
- Whether the committed mirror is CSV, markdown, or both (D-02).
- How "iterative loop" rounds are sequenced (single review round vs. multiple) — keep it human-in-the-loop per ROADMAP cross-cutting constraints.

</decisions>

- `data-pipeline/python/fetch_destatis.py`: emits `destatis_variables.csv` / `destatis_nuts3_export.csv` for expert review — the working template for "variable-level rows reviewers approve."

- `/gsd:add-backlog`: the GSD command that produces the 999.x backlog items this phase outputs (D-10).

### Established Patterns
- Documentation lives in `docs/` (human-facing) and `.planning/research/` (planning research); the catalogue + its mirror should follow these conventions.
- `sources.yaml` `kind:` field (`raster` / `vector`) classifies pipeline paths — the integration-sketch "pipeline path" field (D-11) maps onto this vocabulary, with `tabular` as the new path for statistical sources like DESTATIS.

### Integration Points
- Output: `/gsd:add-backlog` (999.x items) — the hand-off into the GSD planning system.
- Supersedes: `docs/data-sources.md` becomes the formalized catalogue's predecessor.
- Future targets (out of scope here): `sources.yaml` declarations + new `build_*.py` scripts per approved source.
