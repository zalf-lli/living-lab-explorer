## Catalogue Format

### Concrete Column Schema

The catalogue should use **two tabs** in `variables_catalogue.xlsx` (the file already has a `spatial_data` tab — expand it):

**Tab: `source_catalogue`** — one row per source/layer/variable entry

The column set is split into four groups:

#### Group A — Identity (verified facts, columns 1–5)
| Column | Type | Example |
|--------|------|---------|
| `source_id` | machine key | `invekos_hesse_landscape` |
| `source_group` | thematic bucket | `IACS / InVeKoS` |
| `source_name` | human label | `InVeKoS Hesse — Landscape Elements 2024` |
| `layer_or_variable` | specific item within source | `Landschaftselemente_2024` |
| `already_integrated` | flag | `yes / no / in-progress` |

#### Group B — Source-stated facts (verified, each row must have a citation URL) [D-03]
| Column | Type | Notes |
|--------|------|-------|
| `spatial_coverage` | text | e.g., "Hesse (Germany)" |
| `temporal_coverage` | text | e.g., "2020–2025, annual" |
| `access_method` | enum | `WFS` / `WCS` / `OGC-download` / `FTP` / `Zenodo` / `REST-item` / `Nextcloud` / `ArcGIS-Hub-REST` / `manual-download` |
| `access_url` | URL | Canonical endpoint |
| `format` | text | e.g., `GeoParquet` / `Shapefile-zip` / `GeoTIFF` |
| `license` | SPDX or plain text | e.g., `CC-BY-4.0` / `GeoNutzV` / `DL-DE-BY-2.0` |
| `update_cadence` | text | e.g., "Annual (April)" |
| `citation_url` | URL | The exact URL the AI fetched to establish these facts |

#### Group C — AI assessment (advisory, D-03) [clearly labelled in header row with "(AI)" prefix]
| Column | Type | Notes |
|--------|------|-------|
| `(AI) ll_relevance` | text | which of the 5 LLs are covered; if coverage is state-level, list relevant states |
| `(AI) pipeline_path` | enum | `raster` / `vector` / `tabular` |
| `(AI) integration_complexity` | enum | `Low` / `Medium` / `High` |
| `(AI) integration_notes` | text | key caveats, auth requirements, size warnings |

#### Group D — Review decision (filled by human, D-06)
| Column | Type | Notes |
|--------|------|-------|
| `decision` | enum | `include` / `defer` / `reject` |
| `priority` | enum | `High` / `Med` / `Low` |
| `rationale` | text | brief free-text |
| `reviewer_comments` | text | free-text for stakeholder notes |

**Full column order (21 columns):**
```
source_id, source_group, source_name, layer_or_variable, already_integrated,
spatial_coverage, temporal_coverage, access_method, access_url, format,
license, update_cadence, citation_url,
(AI) ll_relevance, (AI) pipeline_path, (AI) integration_complexity, (AI) integration_notes,
decision, priority, rationale, reviewer_comments
```

The `(AI)` prefix in column headers is the D-03 visual separator. Reviewers learn once: "trust columns without `(AI)`; treat columns with `(AI)` as AI estimates."

### CSV Mirror Pattern

`data/source_catalogue.csv` — regenerated by `data-pipeline/python/export_source_catalogue.py`, using the same pattern as `export_variables.py`:

- Script contains a Python list-of-tuples for the fact+assessment columns (populated during research).
- Decision columns (`decision`, `priority`, `rationale`, `reviewer_comments`) are always emitted as empty strings — reviewers fill them in the xlsx.
- Script takes no args, has no network calls; safe to run offline.
- `json.dumps(..., sort_keys=True)` convention from CLAUDE.md does not apply here (CSV, not JSON), but `sort_keys` equivalence is achieved by keeping the tuple list sorted by `source_group` then `source_id`.

**Mirror drift prevention:** The xlsx is the review working copy. After review, the plan should instruct the reviewer to re-export the CSV from xlsx using the script (or pandas `to_csv`) so the committed mirror reflects final decisions. The planner should add a Wave 3 task for this.

## Evidence-Chain / Provenance Pattern

### The Core Discipline

Every row in Group B (source-stated facts) must have a non-empty `citation_url` that the AI (or the probe script) actually fetched to confirm the claim. The citation URL is the anchor. If a fact cannot be traced to a specific URL, it goes in the AI-assessment column instead, with a note explaining it is an estimate.

**Concrete implementation:**

```
spatial_coverage: "Hesse (Germany)"
citation_url: "https://inspire-geo.ibykus.net/geoserver/lawi/wfs?service=WFS&version=2.0.0&request=GetCapabilities"
# Verified: BoundingBox in FeatureTypeList, 2026-06-01
```

```
spatial_coverage: [ASSUMED: Germany-wide, all 20 EU member states]
# -> move to (AI) ll_relevance column, NOT to spatial_coverage
```

### Wave 2 Research Protocol (for the planner)

For each source in the Wave 2 research task:
1. Fetch the authoritative URL (GetCapabilities, Zenodo API, REST item, FTP README).
2. Extract only what is stated in the fetched document.
3. Write fact columns from the fetched content; write citation_url = the fetched URL.
4. Write AI-assessment columns separately, explicitly noting what was inferred vs. stated.
5. Flag any fact that could not be confirmed as `[needs-verification]` in the fact column rather than silently guessing.

### xlsx vs. CSV Mirror Drift

The xlsx is edited by reviewers (decision columns). The CSV mirror should be regenerated after each review round, not kept manually in sync. The plan should:
- Wave 2: AI populates xlsx fact+assessment columns via `export_source_catalogue.py`; exports CSV.
- Wave 3: Reviewer fills decision columns in xlsx; regenerates CSV using `pandas df.to_csv()` or the same export script reading back the xlsx.

Both the xlsx (for the review session) and the CSV (for the permanent record) should be committed.

## Backlog Hand-Off

### `/gsd:add-backlog` Structure

From the GSD documentation [CITED: github.com/gsd-build/get-shit-done/blob/main/docs/COMMANDS.md]:

`/gsd:add-backlog` creates a 999.x phase directory (e.g., `.planning/phases/999.1-invekos-hesse-vector-integration/`) and adds a ROADMAP.md entry with status `(BACKLOG)`. The item can later be promoted via `/gsd:review-backlog`.

### Integration Sketch Shape (D-11)

Each backlog item should include a brief integration sketch. The sketch maps directly onto the `sources.yaml` vocabulary. Recommended content:

```yaml
# Integration sketch for backlog item (plain text block in ROADMAP.md entry description
# or in a SKETCH.md in the phase dir)

source_name: InVeKoS Hesse — Landscape Elements / Reference Parcels
access_method: OGC WFS (GeoServer 2.0)
endpoint: https://inspire-geo.ibykus.net/geoserver/lawi/wfs
feature_types:
  - lawi:Landschaftselemente_2024
  - lawi:LPIS-Referenzparzellen_2024
data_format: GML via WFS GetFeature (or Shapefile via SHAPE-ZIP outputFormat)
pipeline_path: vector   # sources.yaml kind: vector
ll_coverage:
  - north-hessian-loess
  - hessian-low-mountain
complexity: Medium  # WFS pagination needed; CRS alignment to EPSG:4326; clip to LL bboxes
auth: none (CC BY 4.0)
integration_notes: >
  Use build_vector.py pattern. WFS may require bbox filtering per LL to avoid
  downloading all of Hesse. Test with GetFeature + BBOX parameter first.
  Landscape elements layer contains hedgerows, field margins — high value for
  agri-environmental indicators.
```

## Common Pitfalls

### Pitfall 1: Mixing AI Assessment into Fact Columns

**What goes wrong:** AI summarizes a GetCapabilities XML and writes "spatial coverage: Germany, suitable for Uelzen LL" — the "suitable for Uelzen" inference is AI-assessed, not source-stated.
**Why it happens:** Natural language summaries blend reported facts and inferences.
**How to avoid:** The column schema enforces separation. The `(AI) ll_relevance` column takes the inference; `spatial_coverage` takes only what the GetCapabilities BoundingBox or service abstract states.
**Warning signs:** Any row where `spatial_coverage` mentions an LL slug directly (LL slugs are not in source metadata — they are derived from NUTS-3 overlap).

### Pitfall 2: Exhaustive Enumeration of Large Portals

**What goes wrong:** The Wave 2 task for DWD CDC attempts to list all 400+ climate parameters available.
**Why it happens:** GetCapabilities/FTP directory listing returns everything.
**How to avoid:** D-05 bound is enforced in the task description. Task must say "enumerate only: daily temperature (TT_TU), daily precipitation (RR), and gridded precipitation (HYRAS-DE) for stations within 50 km of LL NUTS-3 centroids."
**Warning signs:** More than 10 rows in the catalogue for a single source family.

### Pitfall 3: Dead/Unstable Portal URLs

**What goes wrong:** A WFS URL that worked at research time returns 404 at integration time (e.g., Hesse endpoint maintained by a contractor).
**Why it happens:** German state geoportal WFS endpoints are operated by third parties (EFTAS, ibykus) and change without notice.
**How to avoid:** Record the `citation_url` as the metadata page URL (e.g., `geoportal.hessen.de/spatial-objects/886`), not just the service URL. The metadata page will update if the service moves. Integration sketches should say "verify WFS URL from metadata page before building."
**Warning signs:** Service URL contains a company subdomain (e.g., `ibykus.net`) rather than an official `hessen.de` or `geobasis.de` domain.

### Pitfall 4: xlsx vs. CSV Mirror Drift

**What goes wrong:** Reviewer edits decision columns in xlsx; someone forgets to regenerate the CSV; they diverge.
**Why it happens:** Two copies of the same data without an automated sync.
**How to avoid:** The Wave 3 task explicitly includes "regenerate CSV from xlsx and commit both." The plan should not allow a "review complete" checkpoint without verifying CSV was regenerated.

### Pitfall 5: AI Fabricating Coverage or Licensing Facts

**What goes wrong:** AI writes that a source covers a specific NUTS-3 region or has "open access" when the source actually restricts bulk download.
**Why it happens:** AI training data includes papers and blog posts about sources, which often describe intended coverage loosely.
**How to avoid:** Mandatory `citation_url` column. Any fact without a URL in `citation_url` is not a verified fact and must go into the `(AI)` assessment column. The planner should add a checklist item: "every source_catalogue row has a non-empty citation_url before Wave 3 begins."

### Pitfall 6: Thünen Nextcloud Access Failure

**What goes wrong:** The Nextcloud share may require an institutional network (ZALF VPN) or may have expired.
**Why it happens:** Nextcloud public shares can be password-protected or have expiry dates.
**How to avoid:** Wave 2 must attempt WebDAV PROPFIND first; if ECONNREFUSED or 401, flag for human to provide alternative download. The ResearchSquare preprint DOI provides an alternative citation path if the Nextcloud is inaccessible: the 2023 Zenodo record (`https://zenodo.org/records/15055561`) appears to be the same Thünen crop-type dataset for 2023 as a COG.
