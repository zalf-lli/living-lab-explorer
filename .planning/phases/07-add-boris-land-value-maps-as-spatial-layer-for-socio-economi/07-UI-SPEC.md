### Choropleth Value Ramp (D-01, D-02, D-03 — 6 fixed quantile buckets, teal → orange)

Per D-03 ("derive from existing `theme.js` tokens... teal→orange... minimize new colors" — Phase 6 D-10/D-11 precedent), the ramp uses **six existing tokens, zero newly invented hex values**, ordered low → high value:

| Bucket (low→high) | Token | Hex | Bucket (low→high) | Token | Hex |
|---|---|---|---|---|---|
| 1 (cheapest) | `C.tealBg` | `#00413f` | 4 | `C.tealLight` | `#00b3ad` |
| 2 | `C.teal` | `#005754` | 5 | `C.orangeDark` | `#dc4b14` |
| 3 | `C.tealMid` | `#008581` | 6 (most expensive) | `C.orange` | `#eb5b25` |

**Rationale:** teal = "cool/cheap", orange = "hot/expensive" is an intuitive metaphor and reuses the app's two existing hue families end-to-end (no new hue introduced). The visible jump between bucket 4 (cyan-teal) and bucket 5 (red-orange) is intentional — it maximizes discriminability at the two ends of the value range, which matters because D-05 mandates showing *all* zone types (residential through forest), producing a wide value spread within one LL.

**Stroke (all value buckets):** `rgba(2,35,34,0.35)` (dark, low-opacity — neutral, does not compete with the ramp), weight `0.4` (thinner than soil's `0.6` because zone counts run into the tens of thousands — thick strokes at that density visually merge into solid dark mass). `fillOpacity: 0.78` (BORIS is a full-tab layer like soil, not a translucent overlay like protected-areas, so higher fill opacity is correct).

**Hover state:** `fillOpacity → 0.92`, stroke weight → `0.7` (mirrors protected-areas' hover-emphasis pattern). **Flagged risk, not a locked decision:** the two Brandenburg LLs have 19,083 and 30,018 zones respectively — an order of magnitude above protected-areas' 362-feature precedent that already required `L.canvas()`. If per-feature `mouseover`/`mouseout` binding measurably degrades interaction latency during implementation, the executor may disable hover-emphasis (keep tooltip-on-hover, drop the style-swap) for those two LLs specifically — this is a performance escape hatch, not a visual-contract change, and must be logged if exercised.

### "No current value" style (D-08 — one deliberate new neutral addition)

No neutral/grey token exists anywhere in `theme.js` (the palette is teal/orange/green/lime + tinted surfaces only). A "no data" cell rendered in any ramp color would be misread as a real (if extreme) value, which D-08 explicitly forbids ("distinct... style... rather than being dropped"). This phase therefore introduces **exactly one new color pair**, clearly flagged as the sole exception to "zero new colors":

| Role | Hex | Notes |
|---|---|---|
| No-data fill | `#d8d8d2` | New — neutral warm-grey, deliberately outside every existing hue family so it cannot be mistaken for a ramp bucket |
| No-data stroke | `#9a9a90` | New — same family, darker, dashed (`dashArray: '3,3'`) |

Fill opacity `0.55` (lower than value zones, to read as visually "muted"/secondary information). **Not a true diagonal hatch pattern** — Leaflet's `L.canvas()` renderer (mandatory here per the Volume Problem, see Performance section) does not expose a hatch/pattern fill primitive the way SVG does; a flat muted grey + dashed border is the achievable equivalent and is the specific, locked answer to CONTEXT's "exact gray/hatch treatment" discretion item.

## Layer Identity & Data Structure

**Layer ID:** `economic` (existing `LAYERS` entry, converted from `type: 'placeholder'` to `type: 'vector'` — no new tab, no new layer ID; D-domain paragraph)
**Type:** vector (GeoJSON), full-tab layer (like `soil`), **not** an overlay (unlike `protected-areas`)
**Data loading:** Lazy, on tab activation, mirroring `soilUrl`'s `useMemo` gate in `LLMap/index.jsx` (only fetch when `layer === 'economic'`)
**Stacking:** Sole vector layer for the `economic` tab; renders above the mask + basemap, below the boundary outline — same z-order as the `soil` branch
**Rendering technique:** **Imperative `L.canvas()` layer** (mirrors `ProtectedAreasLayer`, NOT the declarative `<GeoJSON>` component `soil` uses) — mandatory because per-LL zone counts (1,668–30,018, see `07-RESEARCH.md` §5.1) are 5×–80× higher than protected-areas' 362-feature precedent that already required Canvas

### Runtime asset

`app/public/data/geojson/boris-{ll-slug}.geojson` — one FeatureCollection per LL, produced by the pipeline's WFS fetch + harmonization step (`fetch_boris.py` / `boris_semantics.py`, per `07-RESEARCH.md` Architecture Patterns). Exact pipeline-side property trimming, coordinate precision, and simplification tolerance are **pipeline/planner concerns** (Open Question 1 in RESEARCH.md), but the **frontend-facing property contract** this UI-SPEC depends on is:

```json
{
  "type": "Feature",
  "geometry": { "type": "Polygon", "coordinates": [...] },
  "properties": {
    "bodenrichtwert": 220.0,
    "has_current_value": true,
    "stichtag": "2024-01-01",
    "usage_type_code": "1100",
    "usage_type_en": "Residential building land",
    "usage_type_de": "Wohnbauflaeche",
    "development_status_en": "Building-expectation land",
    "development_status_de": "Bauerwartungsland",
    "bodenrichtwertNummer": "00260104",
    "ll_slug": "rheingau"
  }
}
```

**Frontend contract requirements (blocking for the pipeline task, not this UI-SPEC's to relax):**
- `bodenrichtwert` MUST be a plain number (EUR/m²) or `null` — never a string — so client-side quantile math (`Array.sort((a,b) => a-b)`) works without parsing
- `has_current_value` MUST be a boolean the frontend can branch on directly for the D-08 no-data style, rather than the frontend re-deriving recency itself
- `usage_type_en`/`usage_type_de` and `development_status_en`/`development_status_de` MUST already be the harmonized canonical vocabulary (D-11) — the frontend never branches on raw BB/HE codes
- Raw `usage_type_code` retained only as a provenance field (never rendered), same pattern as BUEK's `SYM_NR`/`GEN_ID`

## Choropleth Value Encoding — Quantile Buckets (D-02, D-09)

**Computed client-side**, per the RESEARCH.md recommendation (`computeQuantileBuckets`, mirrors `buildSoilLegendEntries`'s existing hand-rolled style) — **locked choice, resolving the "client-side vs. pipeline-precomputed" discretion item.** Rationale: zero pipeline re-run needed if bucket count ever changes; D-09's per-LL independence falls out for free since each LL's GeoJSON is already fetched/processed independently.

**Bucket count: exactly 6** (top of D-02's "5-6" range, locked to remove ambiguity — a fixed count is required for "consistent legend shape across all 5 LL pages").

**Algorithm contract:**
1. Collect `bodenrichtwert` values from features where `has_current_value === true` only (D-08 zones are excluded from quantile math, not just from display)
2. Sort ascending; compute 7 breakpoints (min, 5 internal quantile cuts, max) → 6 closed ranges
3. Round each breakpoint to the nearest whole `€/m²` for legend display (raw unrounded breakpoints still gate style-function bucket assignment — only the *label* is rounded)
4. **Edge case — collapsed buckets:** if rounding produces two adjacent buckets with an identical label (common when many zones cluster at the same low price), render only one legend row spanning both underlying buckets rather than two rows with duplicate text. The style function still assigns 6 distinct fill colors to features; only the *legend* collapses visually-identical labels.
5. Assign fill color by bucket index (table above); assign the no-data style (previous section) whenever `has_current_value === false`, bypassing the bucket assignment entirely

**Legend entry shape** (extends the existing generic `{value, en, de, color}` shape `MapLegend.jsx` already renders — **no `MapLegend.jsx` code change required**, only the `entries` array passed to it changes shape from static per-layer arrays to dynamically computed ones, exactly as `soilLegendEntries`/`protectedAreasLegendEntries` already do):

```javascript
// 6 value-bucket entries (D-04: exact €/m² range as the label)
{ value: 'bucket-0', en: '0-4 €/m²', de: '0-4 €/m²', color: '#00413f' }
{ value: 'bucket-1', en: '4-9 €/m²', de: '4-9 €/m²', color: '#005754' }
// ... buckets 2-5 ...
// 7th entry, always last, only rendered if any no-data zones exist in the collection
{ value: 'no-data', en: 'No current value', de: 'Kein aktueller Wert', color: '#d8d8d2' }
```

Legend note (D-10) passed via the existing `note` prop on `<MapLegend>` (exactly as `soil`/`protected-areas` already do): `t('legend.economic.note')`.

## Tooltip Interaction (D-12)

**Trigger:** Hover over any zone polygon
**Rendering:** Sticky HTML tooltip via `layer.bindTooltip(wrapper, { sticky: true, direction: 'top', opacity: 0.95 })` — identical binding call to `bindSoilTooltip`/`bindProtectedAreasTooltip`; new function `bindEconomicTooltip(feature, layer, t, lang)` follows the same `createTooltipRow()` composition pattern (no new tooltip primitive)

**Row order (locked, resolves the "tooltip layout beyond the three required fields" discretion item):**

1. **Title row** (bold, `createTooltipRow(doc, '', formattedValue, true)`): the formatted value itself, e.g. `"220 €/m²"` via `Number(value).toLocaleString(lang === 'de' ? 'de-DE' : 'en-US')`. **If `has_current_value === false`:** title row instead shows `t('map.economicTooltip.noCurrentValue')` (no numeric value rendered at all — never show a stale/historical number as if current, per Pitfall 3 in RESEARCH.md)
2. **Usage type row** (label: `t('map.economicTooltip.usageType')`, value: `getLocalizedValue(props, 'usage_type', lang)`)
3. **Valuation date row** (label: `t('map.economicTooltip.valuationDate')`, value: formatted `stichtag` via `new Date(props.stichtag).toLocaleDateString(lang === 'de' ? 'de-DE' : 'en-US')`) — **omitted entirely** when `has_current_value === false` and no Stichtag exists, or shown with an explicit "(historical)" qualifier if a stale Stichtag IS present on a no-current-value zone (pipeline may still ship the last-known Stichtag for context — frontend renders it only if the property is non-null, with the qualifier)

**No zone-reference-code row** (D-12 explicit exclusion — `bodenrichtwertNummer` is provenance-only, never rendered)
**No development-status row** — D-12 lists exactly three fields; development-status/Bauerwartungsland is intentionally tooltip-*excluded*, visible only insofar as it's implicitly one more zone among all zones (D-07), not called out as its own row

**Styling:** identical to existing tooltip conventions — max-width 280px, line-height 1.35, 10px/700/uppercase micro-labels, 12px/400 values, 4-8px row margins (no new tooltip CSS).

## Accessibility & Interaction

- Tooltips dismiss on Escape (existing pattern, unchanged)
- Legend swatches: dark stroke on the "no current value" grey (`#9a9a90` border on `#d8d8d2` fill) meets WCAG AA contrast against the `#e5f5ee` legend strip background
- The 6-bucket teal→orange ramp is **not colorblind-differentiable by hue alone at the two-token boundary** (teal-light `#00b3ad` vs orange-dark `#dc4b14` — this is the intended sharp visual break, and is also the boundary most likely to remain distinguishable for red-green colorblind users since it is a teal-to-red/orange transition, not a red-green one; no additional accessibility mitigation needed beyond what the sequential hue choice already provides)
- No new ARIA roles; `<MapLegend>` remains plain `div`/`span` markup, unchanged accessibility surface

## Performance & Constraints

- **Canvas renderer is mandatory, not optional** — `L.canvas()` per-tab pane, exactly like `ProtectedAreasLayer`. The declarative `<GeoJSON>` component `soil` uses (hundreds of features) does not scale to BORIS's 1,668–30,018 zones/LL; using it here would silently degrade to one SVG `<path>` per polygon and freeze the two Brandenburg LLs' tabs.
- **Lazy load only** — GeoJSON fetched exclusively when `layer === 'economic'` is active; no upfront fetch; matches D-07's precedent from the protected-areas overlay (lazy-on-activation), even though BORIS is a tab not an overlay.
- **Geometry fidelity is a pipeline decision, not a frontend one** — RESEARCH.md's Open Question 1 (simplification tolerance / coordinate precision for the two Brandenburg LLs) is unresolved and explicitly flagged as blocking for the *plan*, not this UI-SPEC; this contract's visual/interaction rules apply unchanged regardless of how that question resolves.
- **Hover-emphasis is a flagged, revisable performance escape hatch** (see Choropleth Value Ramp section above) — tooltip-on-hover must always work; the emphasis style-swap on hover may be dropped for the two Brandenburg LLs specifically if profiling shows it's needed, and must be logged as a deviation if exercised.

## Decisions Pre-Populated from CONTEXT.md

| Decision ID | Requirement | UI Implication |
|---|---|---|
| D-01 | Continuous choropleth, not categorical | New teal→orange 6-bucket ramp (this document, Color section); first continuous-value legend in the app |
| D-02 | Quantile bins, 5-6 classes, computed across all zones | Locked to exactly 6 buckets; combined-zone quantile math (no per-usage-type split) |
| D-03 | Sequential ramp derived from `theme.js`, minimize new colors | 6 existing tokens reused (`tealBg→teal→tealMid→tealLight→orangeDark→orange`); zero new value-ramp hex codes |
| D-04 | Legend shows exact €/m² range per bucket | `en`/`de` legend labels are formatted ranges (e.g. "4-9 €/m²"), not gradient endpoints |
| D-05 | Show ALL zone types, not agricultural-only | No usage-type filter in the fetch or the frontend; wide value range is expected and handled by quantile binning |
| D-06 | Usage type is tooltip-only, not a second visual channel | No hatching/border-per-type; fill color encodes value only |
