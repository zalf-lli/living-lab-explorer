  <context>
This phase's data is 5x to 80x denser than any vector layer previously integrated: verified per-Living-Lab
zone counts run from 1,668 (rheingau) to 30,018 (east-brandenburg), against a 362-feature ceiling for the
protected-areas layer. The largest per-Living-Lab vector GeoJSON committed today is
`data/geojson/protected-areas-east-brandenburg.geojson` at 7,582,567 bytes, and every output file is
committed twice (`data/geojson/` and `app/public/data/geojson/`).

07-CONTEXT.md D-08 requires that zones with no current land value are still shown, in a distinct neutral
style, rather than dropped — so the recency rule does not remove data, it only changes how many zones are
rendered as neutral rather than coloured. D-11 requires one shared bilingual usage-type vocabulary across
both states before anything reaches the frontend.

Present the developer with the measured tables from `07-SPIKE.md` verbatim before listing the options below.
  </context>
  <options>
    <option id="w01-fit-budget">
      <name>W-01 A: use the lowest-loss variant that fits an 8 MB per-Living-Lab-per-copy budget</name>
      <pros>Keeps BORIS at or below the largest vector layer already committed; total repository impact stays proportionate to the existing `data/geojson/` tree; no new build machinery.</pros>
      <cons>Requires whichever `coordinate_precision`/`simplify_tolerance` combination the spike shows is needed, which may visibly generalise zone boundaries in the two Brandenburg Living Labs.</cons>
    </option>
    <option id="w01-raise-budget">
      <name>W-01 B: accept a larger per-Living-Lab budget in exchange for higher geometric fidelity</name>
      <pros>Zone boundaries stay closer to the source cadastral geometry; simpler pipeline.</pros>
      <cons>Adds the chosen amount twice to a repository whose history is already large; every future clone pays it.</cons>
    </option>
    <option id="w01-structural">
      <name>W-01 C: structural change — render the two Brandenburg Living Labs as per-Living-Lab PMTiles instead of GeoJSON</name>
      <pros>Decouples committed size from zone count entirely; reuses the Phase 6 per-Living-Lab PMTiles build path.</pros>
      <cons>Two different rendering paths for one tab; the client-side quantile bucketing and the D-12 tooltip would need a vector-tile equivalent; materially enlarges this phase.</cons>
    </option>
    <option id="w02-relative">
      <name>W-02 R1: relative — a zone is current when its newest Stichtag year equals the newest year present in that Living Lab</name>
      <pros>Self-calibrating; never marks an entire Living Lab as stale if Brandenburg's publication cadence shifts.</pros>
      <cons>The same zone can flip between current and not-current across pipeline runs; the meaning of the colour differs subtly between the two Brandenburg Living Labs.</cons>
    </option>
    <option id="w02-absolute-2022">
      <name>W-02 R2: absolute — current means Stichtag on or after 2022-01-01 (roughly two biennial cycles)</name>
      <pros>Stable and explainable; tolerates one missed publication cycle.</pros>
      <cons>Becomes progressively more permissive as time passes unless revisited.</cons>
    </option>
    <option id="w02-match-hessen">
      <name>W-02 R3: cross-state consistency — current means Stichtag on or after 2024-01-01, matching Hessen's /2024/wfs vintage</name>
      <pros>The same recency bar applies in all five Living Labs, so the neutral style means one thing app-wide.</pros>
      <cons>Likely marks the largest share of Brandenburg zones as neutral; the spike's R3 column shows exactly how many.</cons>
    </option>
    <option id="w03-approve-map">
      <name>W-03: approve the proposed Hessen-code to canonical-vocabulary mapping as drafted in 07-SPIKE.md</name>
      <pros>Ships the harmonized bilingual contract D-11 requires, with the 44-entry GDI-DE codelist as the canonical target.</pros>
      <cons>Any Hessen code not observed in the three Hessen Living Labs falls to the "Unmapped usage type / Nicht zugeordneter Nutzungstyp" bilingual fallback with the raw code preserved.</cons>
    </option>
    <option id="w03-amend-map">
      <name>W-03: amend specific rows before approval</name>
      <pros>Corrects any mapping the developer knows to be wrong for these regions.</pros>
      <cons>Requires the developer to name each corrected row explicitly.</cons>
    </option>
  </options>
