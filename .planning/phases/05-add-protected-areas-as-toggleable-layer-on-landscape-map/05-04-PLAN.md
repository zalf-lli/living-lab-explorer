Ten keys, each present in both the `en` and the `de` tree. Designation labels are NOT i18n keys —
they live in `PROTECTED_AREAS_LEGEND` in `app/src/data/layers.js`.

Bare leaf names are NOT safe to grep for: `area`, `designation`, `authority` and `established`
already occur in `i18n.js` today inside `soilTooltip` (`waterArea`, `specialArea`) and elsewhere,
so a substring test would pass without a single new key being added. Bare *values* are no safer:
counting `'Protected Areas'` alone cannot attribute the hit to a language tree.

The seventeen `key: 'value'` pairs that prove both trees were populated. Assert on THESE, never
on a bare key name and never on a bare value. `area`, `designation`, `authority` and `established`
all already occur in `i18n.js` today (`waterArea`, `specialArea` and their neighbours), so a bare
key test passes with zero new keys added; a bare value cannot be attributed to a language tree. A
`key: 'value'` pair is scoped to exactly one tree and cannot false-pass. All assertions are
CASE-SENSITIVE and quote-exact (`i18n.js` uses single quotes):
```

count("protectedAreas: 'Schutzgebiete'")                                                == 1
count("protectedAreasLoading: 'Loading protected areas for this Living Lab...'")        == 1

count("protectedAreasError: 'Protected areas data could not be loaded for this Living Lab.'") == 1
count("protectedAreasError: 'Die Schutzgebietsdaten fuer dieses Living Lab konnten nicht geladen werden.'") == 1

count("area: 'Area'")                                                                   == 1

```
Plus the two legend notes, asserted the same way with their full text (`note: '<full EN text>'`
