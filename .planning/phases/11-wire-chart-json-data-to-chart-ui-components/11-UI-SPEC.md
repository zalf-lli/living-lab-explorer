## The Core Problem This Phase Solves

`BarChart.jsx` currently reads `CHART_DATA[layer]` — a hand-written, build-time, per-layer (not per-LL!) placeholder object in `app/src/data/chart_data.js` with a fixed set of bar keys resolved through a dead-end i18n block (`i18n.js`'s `charts.*` namespace, e.g. `charts.agriculture.bars.winterWheat`). Every Living Lab sees the *same* fake bars today.

Phase 9 already produced 25 real, `mock: false` per-(layer, Living Lab) JSON files in `app/public/data/charts/` (verified: `landuse-croptypes-*.json` x5, `buek250-*.json` x5, `io-lulc-landcover-*.json` x5, `boris-*.json` x5, `chelsa-climate-*.json` x5). This phase's entire job is to fetch those real files at runtime and delete the placeholder path — **no pipeline changes** (roadmap scope note).

Two shapes exist and require two different visual treatments:

- `chart_type: "bar"` — agriculture, soil, economic, landscape (`series: [{label:{en,de}, value, pct}]`)
- `chart_type: "line"` — **climate only** (`x_axis` + `lines: [{label:{en,de}, points:[{x,value}]}]`, exactly 2 x-points, up to 4 lines). Climate is currently rendered by `BarChart` with 6 fake "month" bars — that entire code path is wrong for the real data shape and must be replaced by a **new `LineChart` component**, not reused/patched into `BarChart`.

## Data Wiring Contract

### File naming: dataset id, not app layer id

The JSON `layer_id` field equals the app-facing tab id (`agriculture`, `soil`, `economic`, `landscape`, `climate`) — but the **filename** on disk uses the `sources.yaml` dataset id, which is different (e.g. `landuse-croptypes-{slug}.json`, not `agriculture-{slug}.json`). This mapping already exists, codegen'd, in `app/src/data/layer_sources.js`'s `LAYER_SOURCE_INDEX` (keyed by `appLayer`, each entry's `.id` is the dataset id):

| App layer (`layer` prop) | Dataset id (`LAYER_SOURCE_INDEX.get(layer).id`) | File |
|---|---|---|
| `agriculture` | `landuse-croptypes` | `data/charts/landuse-croptypes-{slug}.json` |
| `soil` | `buek250` | `data/charts/buek250-{slug}.json` |
| `economic` | `boris` | `data/charts/boris-{slug}.json` |
| `landscape` | `io-lulc-landcover` | `data/charts/io-lulc-landcover-{slug}.json` |
| `climate` | `chelsa-climate` | `data/charts/chelsa-climate-{slug}.json` |

**Do not hardcode a second copy of this table in the new hook.** Resolve the dataset id from `LAYER_SOURCE_INDEX` at call time: `LAYER_SOURCE_INDEX.get(layer)?.id`. This is exactly the same reuse discipline `StatPanel.jsx` already applies to the same module for its source-attribution footer.

### New hook: `app/src/hooks/useChartData.js`

Mirrors the existing `app/src/hooks/useGeoJSON.js` pattern exactly (module-scope `cache`/`inflight` Maps, same `{data, loading, error}` shape) — do not invent a different async-state shape. One deliberate difference: **a 404 response resolves to `data: null` with no error**, not a thrown error, because the pipeline's own contract (`data-pipeline/README.md`) documents that a chart file may legitimately not exist yet (`sync.py`'s `[chart] skipped - not yet built` case) for a future layer. Any other non-OK status, a network failure, or a JSON parse failure **is** a real error.

```
useChartData(layer, slug) -> { data, loading, error }
```

- Resolves `url = 'data/charts/' + LAYER_SOURCE_INDEX.get(layer).id + '-' + slug + '.json'`
- `fetch(url)` → if `res.status === 404`, resolve `null` (empty, not error)
- If `!res.ok` (any other bad status) or `res.json()` throws → reject (error)
- Cache key is `layer + '|' + slug` (all 25 files are static and immutable per session — cache forever, exactly like `useGeoJSON`)

### Three states, precisely

1. **Loading** — always rendered visibly (never silently blank), even on the single-LL page. Centered text, matches `MapFallback`'s exact style convention (no spinner, no skeleton bars — the app has zero CSS animation anywhere; do not introduce one).
2. **Error** (network/parse/non-404 failure) — always rendered visibly, on every page (single-LL and comparison), regardless of the `minHeightWhenEmpty` prop. Silently hiding a real fetch failure is worse than showing nothing was asked for.
3. **Empty** (404 / no file yet) — preserves today's exact behavior: `return null` on the single-LL page (`minHeightWhenEmpty` unset), visible placeholder block in comparison columns (`minHeightWhenEmpty` set) — this is a pure continuation of Phase 10's existing `minHeightWhenEmpty` contract, not a new mechanism.

## Component Modifications

### `app/src/components/BarChart.jsx` (rewritten, not patched)

- New props: `{ layer, ll, compact = false, minHeightWhenEmpty }` — **`ll` is new and required** (replaces the implicit build-time `CHART_DATA[layer]` lookup; the hook needs `ll.slug`).
- Calls `useChartData(layer, ll.slug)` internally.
- Deletes the import of `CHART_DATA` and the internal per-chart title row (`t('charts.${layer}.title')`) entirely — the wrapping card at every call site already renders a title (`llDetail.distributionTitle`/`llDetail.projectionTitle`, see Copywriting Contract), so the inner title was always a duplicate and there is no longer a fixed per-layer title string to show (categories are open-ended, data-driven).
- **Top-6-plus-Other truncation, applied identically in compact and full mode:** if `data.series.length > 6`, render the first 6 entries as-is (the pipeline contract guarantees `series` arrives pre-sorted descending by `pct`, tie-broken by English label — verified in `compute_economic_chart.py:77`, `compute_soil_chart.py:104`, `compute_landscape_chart.py:87`, `compute_agriculture_chart.py:131` — **the client must never re-sort**), then append one synthetic 7th "Other" bar: `{ label: t('chart.otherCategory'), pct: sum of remaining pct, value: sum of remaining value }`. Below 6 entries, no Other bar. This caps every chart at 7 rows max regardless of layer (agriculture/economic can carry 18-31 real categories; soil 9-14; landscape 7-8).
- **Rank-based color, not category-identity color.** Categories are open-ended and differ per Living Lab (31 distinct usage types across the 5 economic files alone), so no fixed category→color map is possible the way `SOIL_LEGEND`/`LAND_COVER_LEGEND` work for the map. Bar N gets `CHART_RANK_COLORS[n]` regardless of what category occupies that rank; the "Other" bucket always gets the fixed neutral grey below, never a rank color:

  ```
  CHART_RANK_COLORS = [C.limeDark, C.teal, C.greenMid, C.orange, C.tealMid, C.lime]
  CHART_OTHER_COLOR = '#d8d8d2'  // the app's one existing neutral-grey precedent
                                  // (BORIS_NO_DATA_STYLE.fillColor, layers.js:33 —
                                  // theme.js deliberately has no grey token; reuse, don't invent)
  ```
- **Row layout**, left → right:
  1. Category label — widened column (`120px` full / `96px` compact, up from today's `82px`/`64px`), `fontSize: 11, color: C.black, opacity: 0.65`. Real category strings run far longer than the old fixed keys (e.g. "fruit trees and other woody vegetation", "Residential building land") — `overflow: hidden; textOverflow: ellipsis; whiteSpace: nowrap`, plus a native `title={label}` attribute so the full string is available on hover with zero new tooltip machinery (the app has no tooltip primitive outside Leaflet).
  2. Bar track — unchanged size/radius; width `= (entry.pct / topPct) * 100%` where `topPct` is the largest `pct` among the rendered (possibly truncated) set, same relative-scaling approach as today.
  3. Bar value — `{pct.toFixed(1)}%`, locale-formatted (`Number(pct).toLocaleString(locale, {maximumFractionDigits: 1})`), `fontSize: 11, fontWeight: 700, color: C.teal`. Always percent — the old `unit.includes('%')` conditional is deleted, since `pct` is universally 0-100 across all four bar layers now (the raw absolute `value` + unit no longer needs a primary display slot).
  4. New secondary caption directly under the label column (not a new row) showing the raw absolute quantity: `{value.toLocaleString(locale)} {unit[lang]}` at `fontSize: 10, color: C.muted` — e.g. "1,753 zones", "5,092 ha". Omitted for the synthetic "Other" bucket's caption if the sum would be misleading only when `value` itself is meaningless; otherwise show the summed value+unit identically.
- **Spacing fix while this file is touched anyway:** the existing compact row gap is `5px` (`gap: compact ? 5 : 8`, `BarChart.jsx:46`) — not a multiple of 4. Change to `4` (the `xs` token). This is the one pre-existing violation inside a file this phase must edit; nothing else in `BarChart.jsx` changes spacing.
- **Footer source line** — replaces the old literal `t('barChart.source', {unit})` = "Source: placeholder data - {{unit}}" (now provably false) with the already-existing, already-bilingual `t('statPanel.sourceLayer', { provider: layerSource.provider })` pattern (`StatPanel.jsx:202`), reading the same `LAYER_SOURCE_INDEX.get(layer)` entry this component already needs for the dataset-id lookup. Add the same "View source" link style (`color: C.orange, fontWeight: 700`) pointing at `layerSource.url`, if present. No new copy key needed for this line — reuse `statPanel.sourceLayer`/`statPanel.viewSource` verbatim.

### New file: `app/src/components/LineChart.jsx`

New component, `chart_type: "line"`, used only by the climate tab. Props: `{ layer, ll, compact = false, minHeightWhenEmpty }` — same shape as `BarChart` for call-site symmetry (`LLDetail.jsx` picks one or the other by `layer === 'climate'`, see below). Uses the same `useChartData` hook and the same three-state loading/error/empty contract.

- **Hand-rolled `<svg>`**, no library. `viewBox` width flexible (`100%` via a wrapping div), fixed height `compact ? 150 : 200` (the `150` matches `BarChart`'s existing `minHeightWhenEmpty={150}` convention in `ComparisonColumn` for visual parity between the two chart types in the same slot).
- **Exactly 2 x-columns**, positioned at 25% and 75% of the plot width; each x-axis label (`x_axis[i].label[lang]`, e.g. "2041-2070") centered beneath its column, `fontSize: 11, color: C.black, opacity: 0.65` (same token as `BarChart`'s row label).
- **Shared linear y-scale across all lines**, domain `[min(0, ...allValues), max(0, ...allValues)]` plus 10% padding on both ends — the zero-inclusive domain is required because climate change values can be negative (precipitation of warmest quarter runs -6.9%/-9.8% while GDD runs +34.8%/+60.6% in the same file). A dashed horizontal reference line at `y=0`, `stroke: C.mutedLight`, `strokeDasharray: '3,3'`.
- **One `<polyline>` + two `<circle>` endpoints per line**, colored by a **fixed per-variable identity** (not rank — climate has exactly 4 known variables, unlike the open-ended bar categories, so a stable identity mapping is both possible and preferable):

  ```
  CLIMATE_LINE_COLORS = {
    gdd:   C.orange,     // '#eb5b25' — heat family, warm accent
    bio1:  C.orangeDeep, // '#bb3f11' — heat family, distinguished from gdd by depth
    bio12: C.teal,       // '#005754' — water family, cool accent
    bio18: C.tealMid,    // '#008581' — water family, distinguished from bio12 by depth
  }
  ```

  These are the exact same 4 hex values already used by `CLIMATE_HEAT_RAMP`/`CLIMATE_WATER_RAMP` in `layers.js` (no new colors invented) — but note the JSON's `lines[].label` carries text, not a variable id, so match by **label text against `CLIMATE_VARIABLES` id via the existing bilingual label**, or — simpler and more robust — match `lines[i]` to `CLIMATE_VARIABLES[i]` **by array position**, since `compute_climate_chart.py` (per `sources.yaml`'s locked `chart:` stanza order) emits the 4 variables in the same fixed order as `CLIMATE_VARIABLES` every time. Confirm this ordering assumption holds against the real files before wiring (all 5 committed files share the same 4-line order: GDD, mean annual temp, annual precip, precip of warmest quarter) — if a future regeneration reorders them, match by translating `CLIMATE_VARIABLES[i].labelKey` through `t()` and comparing against `lines[i].label[lang]` as a defensive fallback rather than trusting position blindly.
- **Value labels** at each point: `{value >= 0 ? '+' : ''}{value.toFixed(1)}%`, or more precisely `Number(value).toLocaleString(locale, { signDisplay: 'exceptZero', maximumFractionDigits: 1 })` — the exact same formatting call `StatPanel.jsx:152` already uses for its delta tiles. `fontSize: 11, fontWeight: 700`, colored the same as that line.
- **Legend row** above the plot: one chip (8px filled circle, matching the existing per-LL accent-chip convention from Phase 10) + `lines[i].label[lang]` per variable, `fontSize: 11, color: C.black, opacity: 0.65`, flex-wrapped.
- Loading/error/empty states, footer source line: identical treatment and copy to `BarChart` (see above and Copywriting Contract) — both components share the same `chart.*` i18n namespace.

### `app/src/pages/LLDetail.jsx` — three call sites

All three existing call sites (`LayoutSplit:518`, `LayoutStacked:658`, `ComparisonColumn:802`) currently call `<BarChart layer={layer} .../>` unconditionally. Each becomes:

```jsx
{layer === 'climate' ? (
  <LineChart layer={layer} ll={ll} {...sameCompactProps} />
) : (
  <BarChart layer={layer} ll={ll} {...sameCompactProps} />
)}
```

`ll` is already in scope at every call site (all three already pass `ll={ll}` to `StatPanel`/`LLMap` on the same lines). The wrapping card's title text also switches per layer (see Copywriting Contract's `distributionTitle`/`projectionTitle`).

### Deleted as part of this phase

- `app/src/data/chart_data.js` — the entire `CHART_DATA` placeholder module (replaced by real per-LL fetches).
- `i18n.js`'s `charts.*` namespace (EN block `i18n.js:132-188`, DE equivalent) — every key in it (`charts.agriculture.bars.winterWheat`, etc.) described a fixed placeholder category set that real, open-ended per-LL data can never match.
- `i18n.js`'s `barChart.source` key ("Source: placeholder data - {{unit}}") — replaced by reusing `statPanel.sourceLayer`.

### Visual Hierarchy / Focal Point

The bar value (`{pct}%`, `fontWeight: 700, color: C.teal`) is the focal point of every chart row — it is the only bold, colored text in the row, drawing the eye to "how much" before "what" (the category label is deliberately lower-emphasis at `opacity: 0.65`). In `LineChart`, the same role is played by the point value labels (`fontWeight: 700`), with the rank-colored polylines providing secondary shape-based hierarchy. This is a continuation of `BarChart`'s existing emphasis pattern, not a new hierarchy being introduced.

### Unchanged / not touched

- `LayerTabs.jsx`, `LLMap`, `StatPanel.jsx`, `theme.js` — no changes required by this phase.
- `layers.js`, `layer_sources.js`, `climate_legend.js` — read from, not modified (no pipeline/codegen work, per roadmap scope).

## Typography

This phase's new/modified elements use a closed **3-size / 2-weight** system (all three sizes and both weights already exist elsewhere in the app — no new type scale is introduced):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Chart row/axis label (category name, x-axis date range, legend text) | 11px | 400 | 1.2 |
| Chart value label (pct%, line-point value, "Other" bucket value) | 11px | 700 | 1.2 |
| Chart secondary caption (raw absolute value + unit, footer source line) | 10px | 400 | 1.3 |
| Empty/error/loading state heading | 12px | 700 | 1.3 |
| Empty/error/loading state body | 12px | 400 | 1.4 |

Exactly two sizes overlap both roles at 11px (label vs. value) distinguished only by weight (400 vs. 700) — this mirrors `BarChart`'s existing, unchanged row-label/row-value split and is not a new pattern.

**Note on the 10/11/12px spread:** these three sizes sit only 1px apart, which reads as tight in isolation. This is an intentional continuation of the app's existing dense-data-display convention (`BarChart`/`StatPanel` already use this exact 10/11/12px scale elsewhere) rather than a new type scale invented for this phase — distinguishing rows relies on weight and color as much as size.

### Chart Data-Visualization Palette (new — resolves "what color are dynamic, open-ended bar categories" and "what color are the 4 climate lines")

Two distinct palettes, because the two chart types have fundamentally different category stability:

1. **Bar charts (agriculture/soil/economic/landscape): rank-based, not identity-based.** Categories are open-ended per-LL strings (up to 31 distinct usage types in economic alone) with no fixed enum, so color encodes *position in the sorted list*, not *what the category is*. See `CHART_RANK_COLORS`/`CHART_OTHER_COLOR` in Component Modifications above.
2. **Line chart (climate only): fixed per-variable identity.** Exactly 4 known variables exist (`gdd`/`bio1`/`bio12`/`bio18`), so each gets one stable color reused from the existing map-ramp hues (`CLIMATE_LINE_COLORS`, see Component Modifications above) — no new hex values anywhere in this phase.

Zero new hex codes are introduced anywhere in this phase; every color above is either an existing `C.*` token or the one already-established neutral-grey exception (`#d8d8d2`, `BORIS_NO_DATA_STYLE.fillColor`).
