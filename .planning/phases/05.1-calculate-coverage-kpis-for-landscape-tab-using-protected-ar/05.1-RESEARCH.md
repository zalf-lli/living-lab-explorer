## Summary

**The KPI slots this phase needs to fill already exist and are already wired end-to-end — only the
data is missing.** Phase 4 pre-declared two curated KPI entries in `data/destatis_curated_kpis.json`
for the `landscape` tab: `natura2000_ha` and `nature_reserves_ha`, both currently `null` in
`data/destatis_ll.json` for all 5 Living Labs. Both already have `kpi.natura2000_ha` /
`kpi.nature_reserves_ha` i18n labels in `app/src/i18n.js`, both already flow through
`generate_metadata.py::_build_kpi_by_tab()` into `ll_metadata.json`'s `kpiByTab.landscape` array, and
`StatPanel.jsx` already renders whatever non-null value lands there with zero UI changes required.
`.planning/STATE.md` confirms these two fields were investigated exhaustively during Phase 4 and
found to be **"non-Destatis products"** — exactly the gap Phase 5's BfN WFS protected-areas layer is
positioned to close. [VERIFIED: repo read 2026-07-25]

**The single most important technical fact for this phase: Phase 5's committed GeoJSON is
deliberately the wrong shape for a coverage statistic, and must not be summed directly.** Phase 5's
`data/geojson/protected-areas-{slug}.geojson` (per its own D-03 decision) stores **full, unclipped
site polygons** — every protected area that merely *intersects* the LL boundary is stored at its
complete national extent, specifically so the map shows conservation context beyond the LL edge. A
site's `area_ha` property is therefore the site's **total official area**, not the portion that falls
inside the Living Lab. Summing `area_ha` (or summing raw feature geometry area) directly would
produce numbers that overstate true LL-level coverage, sometimes by a large margin for sites that
straddle a boundary. **This phase must clip the Phase 5 output to the LL boundary before computing
area** — the opposite spatial operation from what Phase 5 itself performs, using the exact
`gpd.clip()` pattern `build_vector.py` already uses for BÜK250.

**Overlaps are also real and must be dissolved, not summed.** BfN's own data legitimately has the
same physical parcel double-designated (an NSG that is also inside an FFH/SCI boundary is explicitly
documented in 05-RESEARCH.md §2.4). Summing individual feature areas within a designation category
would double-count these overlaps. `GeoDataFrame.geometry.union_all()` — already used in-repo by
`build_pmtiles.py` for exactly this reason — must dissolve all polygons of the same designation group
into one geometry before an area or clip operation.

**Primary recommendation:** add a new pipeline script (suggested name
`data-pipeline/python/compute_protected_area_coverage.py`) that, per Living Lab: reads
`data/geojson/protected-areas-{slug}.geojson`, reprojects to `EPSG:25832` (the BfN/UTM native CRS,
matching how the rest of this project already reasons about metric area), reprojects+clips against
`data/ll_boundaries.geojson`, dissolves per designation group (`natura2000` = SCI+SPA rows,
`naturschutzgebiet` = NSG rows), computes `.area / 10000` (ha), and writes the two numbers to a
**new sibling JSON file** (`data/protected_area_kpis.json`) rather than patching
`data/destatis_ll.json` in place. `generate_metadata.py::_build_kpi_by_tab()` is then extended with
one small, additive change to prefer this new file's value for exactly these two variable keys. This
avoids the single biggest footgun identified in this research: `fetch_destatis.py`'s
`aggregate_ll()` **regenerates the entire per-LL record from NUTS3 sums on every full re-run**, so an
in-place patch of `destatis_ll.json` would be **silently wiped** the next time someone re-runs the
Destatis fetch.

## 1. Coverage KPI Calculation Approach

### 1.1 What "coverage" means here, precisely

Two related but distinct numbers are possible, and the phase brief's own output spec asks for both
("Calculate coverage percentages" *and* the pre-existing `_ha` slots exist). Both are computed from
the same clipped-and-dissolved geometry, just divided differently:

| KPI | Formula | Existing contract? |
|---|---|---|
| `natura2000_ha` | `area_ha( dissolve(SCI ∪ SPA features) ∩ ll_boundary )` | **Yes** — pre-declared null slot, `landscape` tab, unit `ha` |
| `nature_reserves_ha` | `area_ha( dissolve(NSG features) ∩ ll_boundary )` | **Yes** — pre-declared null slot, `landscape` tab, unit `ha` |
| *(optional)* `protected_area_coverage_pct` | `area_ha( dissolve(SCI ∪ SPA ∪ NSG) ∩ ll_boundary ) / area_total_ha × 100` | **No** — would be a new curated-KPI entry (see Open Questions) |

### 1.2 The clip-then-dissolve pipeline (verified pattern, adapted)

```python
import geopandas as gpd

METRIC_CRS = "EPSG:25832"  # BfN's native CRS; matches Phase 5's own source CRS

protected = gpd.read_file(f"data/geojson/protected-areas-{slug}.geojson")  # EPSG:4326, from Phase 5
protected.geometry = protected.geometry.make_valid()          # CLAUDE.md rule -- re-validate on read
protected = protected.to_crs(METRIC_CRS)

boundaries = gpd.read_file("data/ll_boundaries.geojson").to_crs(METRIC_CRS)
ll_geom = boundaries.loc[boundaries.ll_slug == slug, "geometry"].iloc[0]

def category_ha(frame: gpd.GeoDataFrame, designations: set[str]) -> float:
    subset = frame[frame["designation"].isin(designations)]
    if subset.empty:
        return 0.0                                             # legitimate zero, not "unmeasured"
    dissolved = subset.geometry.union_all()                     # collapse same-category overlaps
    clipped = dissolved.intersection(ll_geom)                   # opposite of Phase 5's D-03 (unclipped display)
    return round(clipped.area / 10_000, 1)                      # m² -> ha, 1dp matches project convention

natura2000_ha    = category_ha(protected, {"Natura 2000 SCI", "Natura 2000 SPA"})
nature_reserves_ha = category_ha(protected, {"Naturschutzgebiet"})
```

`geometry.intersection(ll_geom)` is used instead of `gpd.clip()` here because the operation is on a
single dissolved `shapely` geometry, not a `GeoDataFrame` — `gpd.clip()` is the right tool when
clipping a `GeoDataFrame` (see `build_vector.py`), `intersection()` is the right tool for a single
pre-dissolved polygon. Both use the same underlying GEOS predicate and produce identical area results;
dissolving first means only **one** clip operation per category instead of one per feature.
[VERIFIED: `union_all()` is the exact method already used in `data-pipeline/python/build_pmtiles.py`
line 44; `EPSG:25832` is the confirmed native CRS of the BfN WFS per `05-RESEARCH.md` §1.4]

### 1.3 Why EPSG:25832, not EPSG:4326 or EPSG:3857

- **EPSG:4326** (the CRS Phase 5's committed GeoJSON ships in) is in degrees — `.area` on a
  geographic CRS is a meaningless number and must never be used for hectare statistics.
- **EPSG:3857** (Web Mercator) is what `build_pmtiles.py` reprojects to for a *buffer* operation, but
  it grossly distorts area at ~50-52°N (this project's latitude band) — roughly 60% area inflation —
  and must not be reused for area math even though it appears once elsewhere in the pipeline for an
  unrelated purpose.
- **EPSG:25832** (ETRS89 / UTM zone 32N) is the source CRS Phase 5 fetches from and is confirmed by
  `05-RESEARCH.md` to be accurate for this project's geographic extent (all 5 LLs sit inside or very
  near UTM zone 32N). Distortion within a single UTM zone is well under 0.1% and is the same CRS
  `fetch_protected_areas.py` itself uses before its own `to_crs("EPSG:4326")` reprojection step for
  display — reusing it keeps the area math consistent with Phase 5's own numbers.
  [ASSUMED: no live re-verification against `EPSG:3035` (LAEA Europe, a true equal-area CRS) was
  performed in this research session; if hectare-scale precision below ~0.1% ever matters, `3035` is
  the more defensible academic choice, but the difference is immaterial at this project's scale.]

### 1.4 Percentage denominator: reuse `area_total_ha`, don't recompute LL boundary area

If a percentage KPI is added, its denominator should be the **existing** `area_total_ha` field
already present and non-null for all 5 LLs in `destatis_ll.json` (Destatis/Regionalstatistik
administrative area figures — confirmed non-null for all 5 LLs in this research session), **not** a
freshly computed geometric area of `data/ll_boundaries.geojson`. Two reasons:
1. **Consistency with existing precedent.** `sealed_surface_pct` and `agriculture_pct` (both already
   in the codebase, `fetch_destatis.py` lines ~654, ~992) both divide by `area_total_ha`. A new
   percentage KPI dividing by a *different* "total area" figure (the GISCO-derived boundary polygon
   area) would silently use two different denominators for conceptually identical "% of LL" stats.
2. **`ll_boundaries.geojson` is a simplified/generalized dissolve** of NUTS3 polygons (built by
   `fetch_nuts.py`), not guaranteed to be pixel-identical to the official Kreis administrative area
   Destatis reports. The mismatch is small (generalization/coastline effects, typically well under
   1-2%) but real, and using `area_total_ha` avoids introducing it.

## 3. Integration with `kpiByTab`

### 3.1 The existing read path (zero changes required to the contract itself)

`data-pipeline/python/generate_metadata.py::_build_kpi_by_tab()`:

```python
def _build_kpi_by_tab(slug: str, destatis_ll: dict, curated_kpis: list) -> dict:
    by_tab: dict[str, list] = {}
    for entry in curated_kpis:
        tab = entry["tab"]
        by_tab.setdefault(tab, []).append({
            "key": entry["variable_key"],
            "value": destatis_ll.get(slug, {}).get(entry["variable_key"]),
            "unit": {"en": entry["unit_en"], "de": entry["unit_de"]},
            "genesisTable": entry["genesis_table"],
        })
    return by_tab
```

This iterates `destatis_curated_kpis.json` (already has `natura2000_ha`/`nature_reserves_ha` rows,
`genesis_table: null`) and looks up `destatis_ll[slug][variable_key]`. **The minimal, additive change**
is to merge a second lookup source before this loop runs, preferring the geodata value when present:

```python
PROTECTED_AREA_KPIS_FILE = DATA / "protected_area_kpis.json"

def _build_kpi_by_tab(slug, destatis_ll, curated_kpis, protected_area_kpis):
    by_tab = {}
    for entry in curated_kpis:
        key = entry["variable_key"]
        value = protected_area_kpis.get(slug, {}).get(key)
        if value is None:
            value = destatis_ll.get(slug, {}).get(key)
        by_tab.setdefault(entry["tab"], []).append({
            "key": key, "value": value,
            "unit": {"en": entry["unit_en"], "de": entry["unit_de"]},
            "genesisTable": entry["genesis_table"],
        })
    return by_tab
```

`build_metadata()` gains one more `_load_json_or_empty(PROTECTED_AREA_KPIS_FILE)` call alongside its
existing three loads. This is a ~6-line diff to a well-understood, already-tested function.

### 3.2 The frontend needs zero changes

`StatPanel.jsx` reads `ll.kpiByTab[tab]` generically — it has no knowledge of *where* a value came
from, only that it is `{key, value, unit}`. Once `natura2000_ha`/`nature_reserves_ha` are non-null,
they render automatically with their pre-existing `kpi.natura2000_ha`/`kpi.nature_reserves_ha` i18n
labels (already present in `app/src/i18n.js`, both EN and DE) — no PLAN task should touch
`StatPanel.jsx`, `useLLMetadata.js`, or `i18n.js` for the ha-only scope.

### 3.3 The one visible gap: no "view source" link for these two tiles

`StatPanel.jsx`'s source-attribution disclosure builds `uniqueTables` from
`fields.map(f => f.genesisTable).filter(Boolean)` — since `natura2000_ha`/`nature_reserves_ha` will
always carry `genesisTable: null` (they were never a GENESIS table), they are silently excluded from
that list, same as they are today while `null`. This is graceful degradation, not a crash, but it
means **no in-panel attribution to BfN** appears next to these two numbers — BfN attribution exists
only via the protected-areas map overlay's own `MapInfoControl`, a separate part of the UI. This
research treats fixing that as **out of scope** (per the task brief's explicit UI exclusion) but
flags it for the planner/discuss-phase to decide whether it's acceptable as shipped.

## 4. Aggregation Strategy

### 4.1 Per-LL, not per-NUTS3 — and why that's a deliberate deviation from the pre-wired pattern

`fetch_destatis.py` already lists `natura2000_ha` and `nature_reserves_ha` in its `_SUM` set (line
~967), meaning the *original* Destatis-era architecture expected these to be computed **per NUTS3
Kreis** and summed up to LL level by the existing `aggregate_ll()` function — the same pattern used
for `forest_area_ha`, `farms_count`, etc. **This phase does not need to follow that pattern.** Phase
5's WFS fetch and this phase's clip source (`ll_boundaries.geojson`) are both LL-scoped, not
Kreis-scoped — there is no committed per-NUTS3 protected-areas GeoJSON to clip against. Computing
directly at LL level (§1.2) is simpler, requires no new WFS calls, and is sufficient because the app
only ever displays `kpiByTab` at LL granularity (`useLLMetadata.js` has no per-Kreis view).

**If a future phase ever wants per-Kreis figures** (e.g. a Kreis-level detail view), `data/nuts3_ll.geojson` — "one feature per NUTS3", already produced by `fetch_nuts.py` — could substitute for
`ll_boundaries.geojson` as the clip mask, and the natural `_SUM`/`aggregate_ll()` pathway would then
apply unmodified. Not needed for this phase. [CITED: `data-pipeline/python/fetch_nuts.py` header
comment, line 7]

### 4.2 Dissolve boundary: within-designation, not across-designation, for the `_ha` KPIs

`natura2000_ha` and `nature_reserves_ha` are dissolved **within their own designation group only**
(§1.2's `category_ha()` filters by `designations` set before dissolving). A Natura 2000 site and an
NSG occupying the same physical land legitimately count toward **both** totals — this mirrors how the
original (never-resolved) Destatis tables `32121BJ001` (Natura 2000) and `32141BJ001` (nature
reserves) are two independent official statistics series, not a single combined figure. Only a
**combined percentage KPI** (if added, §1.4) needs an across-all-three-designations dissolve to avoid
double-counting the same physical hectare under two different "is this protected" percentages.

### 4.3 Handling genuinely empty results

Every one of the 5 LLs is confirmed (05-RESEARCH.md §2.3) to have a non-zero count of all three
designations (minimum: Rheingau's 78 total features), so an empty result is not expected in practice
for this project's 5 LLs. Still, `category_ha()` should return `0.0` (a legitimate measurement) rather
than `None`/raise when a filter produces zero features — this matches `05-RESEARCH.md` Pitfall 7's
distinction between "raise on a genuine query bug" (upstream, Phase 5's concern) and "a real,
measured zero is a valid downstream value" (this phase's concern).

| Area of a dissolved multi-polygon | Manual shoelace-formula/triangulation code | `geometry.area` after `.to_crs()` to a metric CRS | GEOS handles this correctly; the only actual risk is forgetting the reprojection step |
| Removing double-counted overlapping polygons | Iterative pairwise `.difference()` loops | `GeoSeries.union_all()` | Already the in-repo pattern (`build_pmtiles.py`); one call, GEOS-correct |
| "How much of this site falls inside the LL?" | Bounding-box ratio approximation | `geometry.intersection(ll_geom)` / `gpd.clip()` | Exact GEOS predicate; `build_vector.py` already proves this pattern works cleanly against `ll_boundaries.geojson` |
| Merging a new geodata-derived value into `kpiByTab` | A parallel, bespoke KPI-injection code path in `StatPanel.jsx` or a new hook | Extend `generate_metadata.py::_build_kpi_by_tab()`'s existing lookup, per §3.1 | Keeps the "one contract, one merge point" architecture Phase 4 already established; the frontend needs to know nothing new |
| Persisting computed values safely across pipeline re-runs | Patching `destatis_ll.json` in place | A new sibling JSON file (`protected_area_kpis.json`) merged at `generate_metadata.py` time | `aggregate_ll()` fully regenerates `destatis_ll.json` on every `fetch_destatis.py --full` re-run; an in-place patch would be silently destroyed |

**Key insight:** every piece of geometry-handling machinery this phase needs (`union_all()`,
`gpd.clip()`, `to_crs()`, a JSON-merge-at-metadata-build-time pattern) already exists verbatim
somewhere in this repository. The only genuinely new code is the small script that chains them
together in the right order (dissolve → clip → area, not clip → dissolve → area — both are
mathematically equivalent, but dissolve-first is one clip operation instead of N).

## Common Pitfalls

### Pitfall 1: Summing `area_ha` (or raw feature geometry area) directly
**What goes wrong:** Coverage figures are inflated, sometimes drastically, for any site that straddles
the LL boundary.
**Why:** Phase 5's `area_ha` property (and the underlying geometry) is the site's full official
extent (D-03: unclipped, by design, for map display context) — not the portion inside the LL.
**Avoid:** Always clip to `ll_boundaries.geojson` (§1.2) before computing area for a KPI; never reuse
the map-layer geometry as-is for a statistic.
**Warning sign:** A `natura2000_ha` value larger than plausible given `area_total_ha` for the same LL.

### Pitfall 2: Computing `.area` in `EPSG:4326`
**What goes wrong:** Nonsensical tiny numbers (degrees², not m²/ha).
**Avoid:** `to_crs("EPSG:25832")` before any `.area` call, matching CLAUDE.md's "always align CRS"
rule.
**Warning sign:** Area values off by many orders of magnitude, or NaN.

### Pitfall 3: Double-counting overlapping same-designation polygons
**What goes wrong:** `natura2000_ha` (or `nature_reserves_ha`) is inflated by counting shared overlap
area twice.
**Why:** BfN's data has confirmed real overlaps (e.g. one NSG whose name also appears associated with
an SPA polygon, per `05-RESEARCH.md` §2.4).
**Avoid:** `union_all()` per designation group before computing area.
**Warning sign:** Sum of individual feature `area_ha` properties (post-clip) noticeably exceeds the
dissolved-geometry area for the same LL/category.

### Pitfall 4: Patching `destatis_ll.json` in place
**What goes wrong:** A future `python fetch_destatis.py` full re-run (e.g. to refresh economic KPIs)
silently regenerates `destatis_ll.json` from `aggregate_ll()`'s NUTS3 sums, wiping the geodata-derived
values back to `null` with no error or warning.
**Avoid:** Write to a separate file (`data/protected_area_kpis.json`) and merge at
`generate_metadata.py` build time (§3.1), never inside `fetch_destatis.py`'s own write path.
**Warning sign:** `natura2000_ha`/`nature_reserves_ha` were populated, then silently reverted to
`null` after an unrelated Destatis re-fetch.

### Pitfall 5: Sequencing — this phase cannot run before Phase 5 executes
**What goes wrong:** `data/geojson/protected-areas-{slug}.geojson` does not exist on this branch as of
this research session (only `buek250-*.geojson` files are present; Phase 5 status is "Planned," not
executed).
**Avoid:** The PLAN for this phase must either (a) explicitly declare a hard dependency on Phase 5
having run first, or (b) be sequenced/executed only after Phase 5's `05-01-PLAN.md` (the WFS fetch
script) has produced real output.
**Warning sign:** `FileNotFoundError` on `protected-areas-{slug}.geojson`, or (worse) a script that
silently no-ops on a missing file and leaves the KPI slots `null` with no error.

### Pitfall 6: Assuming the test suite already guards this feature
**What goes wrong:** `test_destatis_resolved_slots_have_real_values()` explicitly `continue`s (skips)
any curated-KPI entry whose `source_host` is `None` — which both `natura2000_ha` and
`nature_reserves_ha` currently are, and will likely remain under the minimal-change path. **No
existing test fails if this phase's computation silently breaks or never runs.**
**Avoid:** Add a phase-specific test asserting these two fields are non-null across all 5 LLs (§5.1,
point 3) as part of this phase's own PLAN — do not rely on the pre-existing Phase 4 test suite to
catch a regression here.

### Pitfall 7: Re-validating geometry validity after the `to_json()`/`read_file()` round-trip
**What goes wrong:** `intersection()`/`union_all()` can raise `TopologyException` on invalid input
geometry.
**Why:** Phase 5's own script already calls `make_valid()` once (on the raw WFS GML read), but the
GeoJSON write/read round-trip (`to_json()` then `gpd.read_file()`) does not guarantee validity is
preserved bit-for-bit, and CLAUDE.md's rule is "always call `make_valid()` after `gpd.read_file()`" —
this applies to *every* `read_file()` call in the codebase, including this phase's read of Phase 5's
output, not just Phase 5's own read of the WFS response.
**Avoid:** Call `frame.geometry = frame.geometry.make_valid()` immediately after
`gpd.read_file("data/geojson/protected-areas-{slug}.geojson")` in this phase's own script, even though
it feels redundant with Phase 5's script already having done so once upstream.
