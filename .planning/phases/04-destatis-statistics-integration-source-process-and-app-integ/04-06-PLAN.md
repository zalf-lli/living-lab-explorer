<objective>
Plan 04-02 discovered (documented in `04-02-SUMMARY.md`'s "Major Finding") that 16 of 17 D-09
curated KPI fields have no Kreis-level cube on GENESIS-Online, and left a D-15 fallback path
partially scaffolded: `_resolve_curated_kpis()` already attempts `_verify_table(old_table,
base=REGIONALSTATISTIK_BASE)` when Regionalstatistik.de credentials exist, but `_headers()` is
NOT base-aware -- it unconditionally sends Destatis GENESIS credentials (token-as-username, empty
password) to whichever host it's called against, and the credential env-var names it checks
(`REGIONALSTATISTIK_USERNAME`/`REGIONALSTATISTIK_API_TOKEN`) don't match what a human can actually
obtain from Regionalstatistik.de's registration flow: real username + real password (classic
auth), not a token. The user has now registered and placed `REGIONALSTATISTIK_USERNAME` /
`REGIONALSTATISTIK_PASSWORD` in `.env`.

Purpose: make the already-scaffolded D-15 fallback actually functional, and empirically verify how
many of the 15 null KPI slots Regionalstatistik.de can genuinely resolve at Kreis level (it may not
be all of them -- Regionalstatistik.de is state-run and coverage varies by Bundesland; a slot that
still can't resolve after this plan stays honestly null, per D-15's non-negotiable "never silently
drop or fabricate" rule).
Output: `data/destatis_curated_kpis.json`, `data/destatis_nuts3.json`, `data/destatis_ll.json`
updated with any newly-resolved real values; `.env.example` corrected to describe the real
credential shape; test coverage for the base-aware auth branch.
</objective>
