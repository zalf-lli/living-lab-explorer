# Phase 14 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this phase's UI surface:** the Soil tab's map slot (`app/src/data/layers.js`, `soil` entry,
currently a single BUEK250 vector layer) grows a second, mode-selectable raster asset (SQR yield
potential), reached through a new sub-tab row directly under `LayerTabs` (D-02, reusing
`VariablePicker.jsx` verbatim per D-03). The soil tab's KPI tiles go from 1 real + 2 permanently-null
to 3 real tiles (D-15/D-16), and the soil bar chart becomes mode-following (D-20: BUEK chart in Type
mode, a new SQR band chart in Yield mode). The per-LL PDF report's soil section gains a second map +
legend pair (D-18). No new route, no new tab, no new page — this is one tab growing a second mode.

**Visual hierarchy / primary focal point:** unchanged from every other tab — the map is the primary
focal point (largest area, first thing the eye lands on). The Type/Yield sub-tab row is a secondary
control that sits directly above the map, in the exact visual slot the climate tab's variable row
already occupies (same component, same row). The map legend + note is tertiary, directly below the
map. The soil KPI tiles and the mode-following chart are read after the map, never before it — this
ordering is unchanged from every prior tab. D-01 locks the default state: a visitor who never touches
the new control sees exactly today's BUEK map, unchanged.

**KPI tile shape (D-16, Claude's discretion resolved):** both new SQR KPI tiles use `StatPanel.jsx`'s

`groundwater_abstraction_1000m3` tile they sit beside. Using the one-line shape for all three soil
tiles keeps the row visually uniform (no orphaned single two-line tile beside two one-line tiles).

### Ramp contract (D-08, D-09, D-10, D-11) — the core new color surface this phase adds

**One ramp family**, sourced entirely from already-declared `theme.js` tokens (zero new hex values, per
Phase 6 D-10/D-11 and Phase 7 D-03's "minimize new colours" rule) — the lime→green ("keim"/"technik")
family, the one family not already claimed by another raster layer (orange = climate heat, teal =
climate water, teal→orange = BORIS land value):

```
#f2f8e2 (limePale) → #c2e077 (lime) → #9bc72d (limeDark) → #359269 (greenMid) → #225e43 (green)
```

Pale = poor cropland, deep green = prime cropland — sequential, light-to-dark = low-to-high, needs no
legend-reading effort.

**Shared and fixed across all five Living Labs (D-08):** unlike BORIS's per-LL quantile scale, this
ramp is baked identically into every LL's tiles — a cell scoring 70 is the same colour in every Living
Lab. This is a correctness requirement (SQR is a national benchmark, and Phase 10's side-by-side
comparison is only meaningful under a shared scale), not a styling preference — flagged here because it
constrains how the pipeline bakes the palette, which the executor must not silently make per-LL.

**Five equal-width bands (D-11), numeric-range labels only** — no invented quality-class names ("high
yield potential"), because BGR publishes no official class breaks. Band edges `[0, 20, 40, 60, 80, 100]`
over a declared 0–100 scale, with the top band open-ended so the nominal 102 ceiling still colours
correctly (the observed German maximum is 99):

| Band | `key` | Range label (EN = DE) | Colour | `theme.js` token |
|------|-------|-----------------------|--------|------------------|
| 1 | `sqr_band_1` | 0-20 | `#f2f8e2` | `C.limePale` |
| 2 | `sqr_band_2` | 20-40 | `#c2e077` | `C.lime` |
| 3 | `sqr_band_3` | 40-60 | `#9bc72d` | `C.limeDark` |
| 4 | `sqr_band_4` | 60-80 | `#359269` | `C.greenMid` |
| 5 | `sqr_band_5` | 80-100 | `#225e43` | `C.green` |
| — | `sqr_not_rated` | Not rated / Nicht bewertet | `#d8d8d2` | `BORIS_NO_DATA_STYLE.fillColor` |

Labels use an ASCII hyphen, not an en dash, matching the transliteration convention the rest of
`i18n_resources.js` and `sources.yaml` follow.

**Resolved during planning (plan `14-03`): five bands, not six.** This document originally specified six
equal-width bands of 17 and left the executor to either derive a sixth hex or collapse to five. It
collapses to five, for a reason that is not aesthetic: the chart must carry D-21's "Not rated" row, so a
six-band partition would produce a seven-row series, and `app/src/lib/chartSeries.js`'s `MAX_BARS = 6`
would fold that seventh row into an "Other" bucket painted `CHART_OTHER_COLOR`. That would silently
delete the grey class the printed map's bar legend exists to explain. Five bands plus Not rated is
exactly six rows, so `buildDisplaySeries` never truncates. It also lands on round numbers and uses
D-09's five locked ramp stops verbatim, so **no new hex value is invented anywhere in this phase**.

The distinctness requirement still holds and is enforced automatically: `test_sqr_contract.py` asserts a
minimum pairwise CIELAB ΔE76 across the six colours. The measured worst pair is band 1 `#f2f8e2` against
the Not-rated `#d8d8d2` at ΔE76 ≈ 13.4, below the ΔE ≥ 15 threshold quick-task `260804-acf` set for the
soil palette. Both of those colours are locked — D-09 fixes the ramp's pale end and D-10 fixes the grey —
so neither may be re-picked to widen the gap. The gate threshold is therefore 12, the shortfall is
recorded rather than hidden, and the pair is an explicit item on plan `14-14`'s human verification
checkpoint (step 5), whose named fallbacks are a legend separator rule or a documented D-10 deviation to
a darker grey.

**"Not rated" cells (D-10):** muted opaque grey, reusing `BORIS_NO_DATA_STYLE.fillColor` verbatim —
`#d8d8d2` — the codebase's one documented exception to "zero new colours" (Phase 7 already carved this
exception because `theme.js` has no neutral grey). Renders as an explicit bilingual legend entry ("Not
rated" / "Nicht bewertet"), matching BORIS's existing `no-data` legend-entry shape
(`buildEconomicLegendEntries`'s `{ value: 'no-data', en, de, color }` pattern) — **not** transparent,
because in a forested LL most of the map would otherwise fade to basemap, indistinguishable from a
tiling failure.

**Legend entries are pipeline-generated bilingual objects, not i18n keys** — mirroring `CLIMATE_LEGEND`
and `buildEconomicLegendEntries`'s existing pattern exactly (`{ value, en, de, color }`). This applies
to both the 5 numeric-range bands and the "Not rated" row; do not invent a parallel i18n-key-based
legend path for this one layer.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | No form-style CTA in this phase (read-only map + stats). The closest analog is the sub-tab row's **Yield potential** segment — selecting it is the one action that reveals the phase's new content. Label exactly **Type** / **Yield potential** (EN), **Bodentyp** / **Ertragspotential** (DE) — short noun phrases, no verb, matching `VariablePicker`'s existing label convention (`GDD`, `Mean temp.`, not verb phrases). |
| Empty state heading | Not applicable to the map — SQR ships as one national raster with full LL coverage; there is no partial-availability state to design for. |
| Empty state body | If `kpiByTab.soil` is ever empty (e.g. mid-migration), reuse the existing `statPanel.compareEmptyTitle`/`compareEmptyBody` verbatim, unchanged — no new empty-state copy needed. |
| Error state | Raster load failure for the Yield mode: new keys `map.soilYieldLoading` / `map.soilYieldError`, mirroring `map.soilLoading` / `map.soilLoadError`'s exact shape. EN: "Loading yield potential layer…" / "Yield potential layer failed to load." DE: "Ertragspotential wird geladen…" / "Ertragspotential-Ebene konnte nicht geladen werden." Reuse the existing `SoilStatusBadge` component verbatim — no new badge. |
| Destructive confirmation | None — no destructive actions on this tab. |

**Sub-tab row aria-label (accessibility fix, required — RESEARCH.md Pitfall 3):** `VariablePicker.jsx`'s
`aria-label` is currently hardcoded to `t('climate.variableRowLabel')` ("Climate variable"). D-03's "no
modification" framing does **not** cover this — reused verbatim, a screen reader would announce "Climate
variable" on the Soil tab. Add one backward-compatible prop, `ariaLabelKey`, defaulting to
`'climate.variableRowLabel'` (so the existing climate call site changes nothing), and pass a new key
from the soil call site: **`soil.modeRowLabel`**. EN: "Soil map mode". DE: "Kartenmodus Boden".

**Legend note (D-12, mode-resolved, not a static layer property):** one bilingual sentence, rendered by
the existing `MapLegend` note path. Type mode keeps the existing `legend.soil.note` unchanged. Yield
mode gets a new key, **`legend.soilYield.note`**, and must define SQR in plain language (this is D-12's
explicit requirement, not decoration):

EN: "Soil Quality Rating (SQR) scores arable land from 0 to 102 based on soil, climate and terrain —
higher scores mean greater yield potential for staple crops."
DE: "Die Soil Quality Rating (SQR) bewertet Ackerflächen anhand von Boden, Klima und Relief auf einer
Skala von 0 bis 102 — höhere Werte stehen für ein höheres Ertragspotenzial bei Feldfrüchten."

**KPI tile labels (D-16, two new tiles):**

| Key | EN | DE |
|-----|----|----|
| `kpi.sqr_mean_score` | Mean soil yield potential (SQR) | Mittleres Ertragspotential (SQR) |
| `kpi.sqr_rated_area_pct` | Share of area with a yield rating | Anteil mit Ertragsbewertung |

These join `kpi.groundwater_abstraction_1000m3` (existing, unchanged) to fill the soil tab's 3-tile
grid. `StatPanel.jsx`'s generic `t(\`kpi.${field.key}\`)` lookup needs no code change — only these two
new resource entries.

**Mode-aware provenance (D-07, a correctness requirement, not copy choice):** `MapInfoControl` and
`StatPanel`'s sources panel must credit the dataset actually on screen — flipping to Yield swaps the
shown provider/licence/citation from BUEK250's to SQR1000's. Reuses the existing
`statPanel.sourceLayer` ("Source: {{provider}}") string unchanged; only the resolved `layerSource`
object changes per mode (see RESEARCH.md Pattern 1/Pitfall 2 for the resolution mechanism — an
engineering concern, not a new copy string). **A single combined credit line naming both BGR/BGR
products was explicitly rejected by D-07.**

**Licence text is a blocking prerequisite, not settled by this document.** RESEARCH.md found SQR1000 is
governed by BGR's General Standard Terms and Conditions (GSTC/AGB), not GeoNutzV, and Article 3(1)
withholds public-republication rights absent a separate written agreement. The `sources.yaml`
`license:`/`attribution:`/`citation:` strings that ultimately populate `MapInfoControl`'s and
`StatPanel`'s provenance text **must not be finalized, and this layer must not ship on a publicly
reachable deployment**, until a human has confirmed publication rights (see RESEARCH.md's "Licence
Risk" section and Open Question 1). Building and visually verifying the UI locally/on a private branch
is not blocked by this — only public publication is. The executor must treat the licence string as a
placeholder until that checkpoint clears.

**Report caption / narrative copy (D-18):** the report's soil section gains a second figure caption
following the exact pattern of `report.mapHeading` (or the source-aware caption from
`.ll_report_source_text()`) already used for every other tab's map — no new caption *shape*, just a
second instance for the Yield map.

## Phase-Specific Component Contracts

These extend the template's generic sections with the concrete control specs the planner/executor
need, since this phase reuses existing components in a new combination rather than inventing new ones.

### Type/Yield sub-tab row (D-02, D-03, D-04)

- **Reuses `VariablePicker.jsx` directly** — same row directly under `LayerTabs`, same `9px 16px`
  button padding, same active/inactive treatment (700/`C.orange`/2.5px bottom border vs.
  400/`rgba(2,35,34,0.5)`), same `role="tablist"`/`role="tab"` semantics. This is the exact visual slot
  and component the climate tab's variable row already occupies — **not** an on-map floating switcher
  (the ROADMAP's "mirroring Baseline/Change" wording is superseded by D-02; do not use
  `PeriodSwitcher.jsx`).
- Exactly **2 entries**: `{ id: 'type', labelKey: 'soil.mode.type' }`,
  `{ id: 'yield', labelKey: 'soil.mode.yield' }`. Order: Type first (D-01's default), Yield second.
- Only required code change to `VariablePicker.jsx` itself: the new `ariaLabelKey` prop (see
  Copywriting Contract above) — everything else (layout, states, sizing) is unmodified per D-03.
- **Renders once, shared across both Phase 10 comparison columns** (D-04) — it lives in `LayerBar`
  beside the existing climate `VariablePicker` instance (mutually exclusive: soil's row renders only
  when `layer === 'soil'`, climate's only when `layer === 'climate'`, exactly like the existing
  `layer === 'climate'` conditional in `LayerBar`). Mode state (`soilMode`) lives in `LLDetail.jsx`
  beside `useLayerState`/`useClimateControlState` — one instance drives every rendered column.
- Default value: `'type'` (D-01) — a visitor who never touches this control sees exactly today's BUEK
  map. This must be the initial `useState` value, not derived from anything that could momentarily
  render Yield first.

### Map render branch (D-08 through D-13)

- Type mode: **unchanged** — same `GeoJSON` polygon render, same `getSoilStyle`/`bindSoilTooltip`.
- Yield mode: **new raster branch**, structurally the same as the climate raster branch
  (`RasterPmtilesLayer`, keyed by `slug` only — no `variable`/`period` axis, since SQR is one dataset).
  Lazy-load only when `layer === 'soil' && soilMode === 'yield'` (extends the existing "tabs lazy-load
  only when active" pattern — do not fetch both BUEK GeoJSON and SQR PMTiles simultaneously just
  because the soil tab is open).
- Resampling is nearest-neighbour and max zoom is capped low enough that a raster cell stays a visible
  block rather than reading as a smooth surface (D-13) — **this is a visual-quality requirement, not
  only a pipeline concern**: if the executor's build renders the Yield map as apparently continuous
  (no visible cell edges) at its default zoom, that is a Dimension 2 (Visuals) failure, because it
  implies more spatial precision than a 1:1,000,000-scale source product has.
- Loading/error states reuse `SoilStatusBadge` verbatim with the new `map.soilYieldLoading`/
  `map.soilYieldError` keys (see Copywriting Contract).

### Legend (D-10, D-11, D-12)

- Type mode: **unchanged** — existing per-LL dynamic `SOIL_LEGEND`/`soilLegendEntries` + `legend.soil.note`.
- Yield mode: new pipeline-generated `SOIL_YIELD_LEGEND` (or equivalently-named export from
  `layers.js`, mirroring `CLIMATE_LEGEND`'s shape) — 5 numeric-range bands + 1 "Not rated" grey row, all
  as bilingual `{ value, en, de, color }` objects, fed to `MapLegend`'s existing `entries` prop exactly
  as climate/economic already do.
- `MapLegend`'s note prop resolves per mode: `legend.soil.note` (Type) vs. `legend.soilYield.note`
  (Yield) — the call site (`LLMap/index.jsx`'s existing `layer === 'soil' ? t('legend.soil.note') : ...`
  ternary) needs a nested branch on `soilMode`, not a new component.

### KPI tiles (D-05, D-15, D-16)

- **KPI bar does not react to the sub-tab** (D-05) — both Type and Yield modes show the identical 3
  tiles. No `StatPanel` prop change, no mode-awareness in this component at all.
- Final tile set (3, unchanged count from today, composition changed): `groundwater_abstraction_1000m3`
  (existing, real), `sqr_mean_score` (new), `sqr_rated_area_pct` (new). The two permanently-null tiles
  (`n_surplus_kg_ha`, `p_surplus_kg_ha`) are dropped — the tab goes from "1 real number + 2 dashes" to
  "3 real numbers."
- Both new tiles use the existing **one-line** tile shape (label + value only — see Typography above),
  not the two-line delta shape.
- Provenance fallback for the two new tiles must resolve to the SQR1000 `sources.yaml` entry, not
  silently fall through to BUEK's (RESEARCH.md Pitfall 2) — an engineering fix
  (`LAYER_SOURCE_BY_ID.get(field.sourceHost)`), but the **visible consequence is a UI contract**: the
  "View source" link under the `sqr_mean_score`/`sqr_rated_area_pct` tiles must point at BGR's SQR
  product page, never at BUEK250's DOI page.

### Chart (D-19, D-20, D-21)

- **The chart follows the map mode** (D-20) — Type mode shows the existing BUEK soil-group bar chart
  (unchanged), Yield mode shows a new SQR band chart. This is the one place the app's non-map UI reacts
  to the sub-tab (contrast the KPI bar, which deliberately does not, per D-05).
- Visual shape: **identical `BarChart.jsx` component**, no new chart component — same card container,
  same title-row pattern each `LLDetail.jsx` layout already gives its chart slot (`llDetail`'s existing
  `chartHeading/chart.*` conventions), same top-N + rank-colour truncation machinery from Phase 11. The
  5-band + not-rated set is exactly 6 rows, which is exactly `chartSeries.js`'s `MAX_BARS = 6`, so
  truncation never fires and no "Other" bucket can appear — that equality is why the band count is five
  (see the Ramp contract above), not a coincidence to be relied on loosely.
- The chart's bar colours must match the map: use the **same 5-band ramp + grey not-rated colour**
  the map paints with (mirrors `chartColorsFromSoilPalette`'s existing BUEK precedent — bars and
  polygons must be the identical hex, not independently derived).
- The "Not rated" class appears as a grey bar in the chart (D-21) so band shares sum to 100% of the LL
  area, not just the rated share — the bar legend's job is to explain every colour the map shows,
  including grey.
- `useChartData(layer, slug)` becomes `useChartData(layer, slug, mode)` (RESEARCH.md Pattern 1) — this
  is the mechanism, not a new visual; `BarChart`'s props gain a `mode` pass-through from `LLDetail.jsx`.

### Report soil section (D-18)

- Renders **both maps**, full-size, each with its own bar-legend figure (not an inset/thumbnail second
  map — rejected as unreadable at 250m per CONTEXT.md). Layout (stacked vs. side-by-side) is Claude's
  discretion; either is acceptable as long as neither map is visually subordinate to the other (same
  figure width/treatment as the existing single-map soil section gets today, repeated once).
- Each map's legend/caption pulls from the same generated band/colour declaration the app uses (D-22 —
  one shared declaration, not three independent constants) via the existing `report_tokens.json` bridge
  — this is a pipeline/R concern for provenance, listed here only so the executor does not treat the two
  maps' legends as independently stylable.
